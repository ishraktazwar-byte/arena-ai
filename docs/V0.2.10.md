# V0.2.10 — bounded multi-step planning

## Goal-directed skill composition

The provider may choose one goal as before, or return an explicit short plan:

```json
{
  "reason": "Make carried supplies for a later goal.",
  "steps": [
    { "tool": "craft", "args": { "item": "oak_planks" }, "reason": "Use a carried log." },
    { "tool": "craft", "args": { "item": "stick" }, "reason": "Use confirmed planks." }
  ]
}
```

This example is not a built-in storyline or default sequence. The planner chooses
its own goals from current needs, observations, memory, personality and permitted
skills. One request may authorize one to four typed actions. The body decides how
each action executes and whether its current prerequisites are met. The unchanged
crafting skill's server-inventory confirmation determines success, not the plan's
assumption about future ingredients.

## Validation and execution

- Accept legacy single-goal JSON or exactly reason/steps. Reasons stay bounded to
  240 characters; plans allow one to four individually validated typed goals.
- Reject extra fields, unknown tools, nested plans, malformed/sparse step arrays,
  loops, policy overrides and arbitrary code. Arguments are copied, not shared
  with caller-owned objects. All steps validate against the active catalog before
  any action begins; each step validates again against the registry before use.
- Preserve the initial provider-result stale-context barrier. Re-observe between
  actions, while allowing expected position changes caused by earlier successful
  steps rather than treating them as stale provider replies.
- Require known health/food and NORMAL risk for subsequent steps; hunger below 12,
  health loss, dimension change or lifecycle/reflex invalidation discards the tail.
  Existing per-tool safety, inventory, terrain and server checks remain mandatory.
- Only COMPLETED permits a subsequent step. Failure, blocking, cancellation or an
  exception stops the plan. A cooling-down proposal becomes one read-only scan,
  then stops: dependent steps do not run as if their prerequisite succeeded.
- Stop admitting steps after sixty seconds from the planning tick's start, or a
  backwards clock. This is an admission deadline, NOT an overall hard timeout:
  an already-running step keeps its existing arbiter timeout (at most 15 seconds).
  Existing memory I/O is not given a new deadline by this release.
- No overlapping planning/execution. No new provider request after each step or
  immediately after a failure. Subsequent planning follows the existing interval
  and shared daily request budget.

Plans have no persistent execution queue. Death, stop/restart or interruption does
not resume their old tail. Each actual step outcome is stored using existing
schema-7 goal history. Unexecuted steps, arbitrary plan rationale and resumable
commands are not persisted. STRATEGY-PLAN/PLAN-STOP/PLAN-COMPLETE events summarize
progress without logging raw model text. Existing per-goal diagnostics remain.

## Autonomy and limits

Autonomous-world scope still requires no per-area/action approval. Restricted mode
still enforces its actual tool catalog and areas. This release does not broaden
permissions, disable reflexes, invent future item UUIDs or add dynamic argument
substitution. Use one goal when a later step requires discoveries unavailable at
planning time. Tool-level success does not prove an entire high-level objective
is achieved; the next planning cycle receives current observations and outcomes.

Free-only OpenRouter routing, retries, 400 output tokens and the shared request
cap are unchanged. A bounded sequence reduces the need for a separate request for
every small compatible action; it does not guarantee that a free provider produces
useful plans. With AI unavailable, the read-only fallback remains unchanged.

This is ephemeral skill composition, not persistent intentions, learned skills,
branching recovery, complete gathering, farming, settlements or social systems.
Live testing remains deferred; no live Minecraft or real provider calls are made.

## Automated verification

Tests cover backward compatibility, bounded validation, copied arguments, no
partial execution of invalid plans, permission revalidation, step order, single
provider request, actual-only history, failure/exception/cooldown tail discard,
danger/vitals/dimension changes, expected movement, time/clock limits, lifecycle
invalidation, pending-history barriers, no concurrent plans and no stale replay.
Provider tests verify the existing free model/token budget and reject malformed
plans. Integration tests run real guarded crafting against deterministic inventory
fixtures: verified planks feed a stick recipe, while unavailable later ingredients
fail and prevent the remaining tail. No arbitrary plan reason enters logs/history.
