# V0.2.11 — persistent supply objectives

## Intentions survive; commands do not

A planner can now carry a typed stock intention between planning cycles and process
restarts. A plan optionally adds objective:{item,count}, where item belongs to the
advertised finite starter/supply vocabulary and count is an integer from 1 to 64.
The planner chooses the item and amount; there is no default progression or fixed
supply-to-building storyline. Existing single goals and short plans remain valid.
Omitting objective leaves the prior intention unchanged; objective:null explicitly
abandons it. An objective update requires a plan with at least one validated step.

An objective is not an executable task or proof of a world fact. No queued steps,
free-form model rationale or generated code are saved. A future cycle receives the
intention alongside current observations, needs and history, then chooses fresh
steps from the current tool catalog. World/area permissions, survival ownership,
request budgets and per-step safety checks remain unchanged. No approval prompts
are introduced in autonomous-world mode.

## Current progress, not assumed completion

Recall reports active, satisfied_now or unknown based on the current carried
inventory. Only an intact, bounded, valid item list supports a numeric count.
A craft/mining/pickup outcome alone does not establish the target stock level.
Satisfaction can reverse after supplies are used: this initial objective type is
a stock target, not an irreversible accomplishment or a delivery contract.
Inventory evidence is explicitly local observation, not a server snapshot proof
or a guarantee that all counted items are accessible to a particular crafting tool.

Unknown inventory never becomes zero or successful completion. The result carries
source=cloud_intent and requiresFreshPlan=true. Future-dated or 24-hour-old objectives
are excluded from recall. Replacing/reaffirming an objective updates its timestamp;
an older clock-shifted update is rejected rather than overwriting newer intent.
This is a bounded initial intention model, not indefinite long-term goal management.

## Scoped persistence

Memory writer schema 8 reads schemas 1–7. One objective (including an explicit
abandonment marker) is kept per configured world ID and dimension. At most eight
contexts are pinned within the existing 500-record memory budget, so routine
observations cannot immediately evict the current intention. Older contexts can
be evicted when that eight-context limit is exceeded. Resource sightings retain
their existing separate cap. Expiration filters recall; it does not guarantee
physical deletion from all snapshots or backups.

Objective records use the existing serialized, locked, backed-up atomic snapshot
writer. Loads validate schema, type vocabulary, count bounds, source and unique
world/dimension scope. Corrupt primary snapshots recover only from valid backups.
Intent is separately recalled and is not mixed into historical event retrieval.
Current-world resets still require a new MC_WORLD_ID; automatic reset detection is
not added. Objectives do not automatically transfer across dimensions or agents.

## Lifecycle and errors

The complete proposed plan must validate before its objective can be stored.
Stale provider replies cannot install intentions. After awaiting objective storage,
the controller re-observes and repeats the stale-context/lifecycle check before
executing an action. An interruption during the write can leave a valid intention
persisted, but never causes the old action tail to resume. Restart requires a new
planning decision.

Read/write failures use sanitized diagnostics. A storage failure may leave the
previous intention intact while the otherwise valid fresh plan can still execute;
the failure is not presented as successful persistence. If memory is unavailable,
objective_storage_unavailable is emitted. This release does not add a persistent
objective store independent of the existing memory lifecycle or a new I/O deadline.

## Automated checks and remaining work

Tests cover typed validation, compatibility, copy isolation, restart, replacement,
abandonment, current stock assessment, unknown/sparse inventory, scope boundaries,
age/clock rules, retention pressure, context limits, v7 migration, corrupt/duplicate
records, backup recovery, failed/concurrent writes, provider context, invalid-plan
non-persistence, lifecycle/movement changes during writes and sanitized errors.
All previous short-plan, skill, safety, provider and memory regression tests run.

The free-only provider, 400 output-token cap and daily request budget are unchanged.
No live Minecraft connections or real provider calls are claimed. Live testing
remains deferred. Broader long-term objectives, autonomous recovery orchestration,
learning, farming, settlement, social/economic and civilization systems remain
unfinished; this release adds persistent supply intention, not full autonomy.
