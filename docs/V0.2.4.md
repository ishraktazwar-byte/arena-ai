# V0.2.4 — guarded crafting workspaces

## Scope
Adds workspace_options, place_crafting_table and craft_at_table. Placement and
table interaction require explicit MC_WORKSPACE_ENABLED plus area/dimension
permission, independent of MC_MINING permission. The runtime catalog carries
copied, bounded permissions that model arguments cannot change. New results are
historical goal outcomes under memory schema v4, with v1–v3 read compatibility.

### Observation and placement
Bounded same-level discovery lists up to eight visible crafting tables and eight
passing placement candidates. Placement attempts one carried crafting table,
without movement, into a known empty cell with headroom on approved inert ground.
It checks footing, body status, supported elevation, top-face visibility/reach,
entity/body overlap, stable support and a remaining known level escape step.
Crafting tables, containers, falling blocks and other interactive/hazardous
reference blocks are not accepted as placement support.

A held table needs no transfer. For a table elsewhere, a server inventory resync
precedes selection; a main-inventory table moves through one guarded number-key
swap into an empty hotbar slot. The pinned click helper writes that operation
before awaiting, because its clicked source is below slot 36. Full hotbars are
refused, not overwritten. Opening a table selects an empty hotbar slot directly:
Mineflayer unequip is not used because it can toss an item when inventory is full.

After explicit guarded aim, a narrow version-pinned adapter writes the exact
1.21.1 top-face block_place packet. It uses the same sequence=0 convention as the
pinned Mineflayer helpers, but avoids their internal async-look-before-write gap.
Only this tool's validated position/face enters the adapter; it is not an arbitrary
packet execution API for model output. A serializer contract test covers the wire
shape. Live server acceptance is still unverified.

A matching server block_change reporting crafting_table is required for placement
completion. Local cache changes alone are insufficient. Before/after inventory
counts are observations; the result does not assert exclusive causal ownership
or roll back a placement that finishes after cancellation. Multi-block packet
variants are not yet accepted as placement confirmation.

### Automatic opening and crafting
craft_at_table requires an approved, visible existing table. It opens with empty
hand, correlates a server open_window ID with Mineflayer's inventory-ready
windowOpen event, verifies the crafting-window type, then calls the V0.2.3 guarded
crafting handler in the SAME action session. Cleanup closes the known owned
window; there is no open-window handoff across strategic AI intervals.

No initial recipe script is forced on agents: the cloud planner may choose these
tools; the no-AI fallback remains read-only scanning. No automatic walking,
placement-and-crafting chain, full gathering loop, claims/ownership inference,
or automatic table removal is implemented.

### Late-response safety
Minecraft window replies have no request correlation ID beyond the new window's
ID, so an interrupted/timed-out unresolved open quarantines workspace interactions
until a fresh connection. Duplicate/ambiguous opening replies also fail closed.
This quarantine persists through death/respawn; it is not silently reset to allow
a stale response to be attached to a new request.

One persistent coordinator per bot handles late windows. It starts a NEW
priority-2000 window-safety action, which can briefly preempt movement/combat,
instead of allowing stale strategy callbacks to close inventory after losing
ownership. Multiple late windows are serialized; a physics-tick retry can close
a quarantined window if safety ownership was temporarily blocked. No close packet
is sent while dead/disconnected. Listeners are removed on connection end.
If a window was positively associated before interruption, normal owned cleanup
is used without unnecessary reconnect quarantine. Unrelated replacement windows
are not adopted by the completed request. Plugin-generated windows and server
latency still need live validation; response association is not proof of which
physical table a customized server chose to open.

## Automated validation
163 tests pass locally on Node 22.22.3 and Node 24.21.0, plus syntax and whitespace
checks. New coverage includes catalog permissions, malformed coordinates/items,
read-only discovery, region/dimension/support/footing/visibility/occupancy checks,
exit obstruction, server placement evidence, staging/aim cancellation, empty-hand
opening, delayed/ambiguous/unmatched replies, death/respawn quarantine, lifecycle
listener cleanup, packet serialization, safe hotbar staging, full-hotbar refusal,
a simulated automatic-open → real guarded 3×3 crafting-handler flow, and v3→v4
memory migration. Existing tests remain passing. Shared crafting fixtures were
extracted into test-support/ without introducing runtime dependencies.

Windows/Ubuntu CI results will be recorded after the actual release run. No live
Minecraft, Aternos or cloud-provider success is claimed by these tests.

## Limitations
No guaranteed rollback or item-loss-free cancellation. Already-issued slot swaps,
interaction packets and placements can have effects after interruption. Empty
hotbar/main-space and known flat terrain requirements deliberately reject some
otherwise possible actions. `_syncWindow` still uses pinned Mineflayer behavior;
its internal waiter can complete later, but guards prevent subsequent tool writes.
No general construction, smelting, farming, settlements, economy, diplomacy or
complete emergent civilization implementation is delivered in this version.
