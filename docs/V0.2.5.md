# V0.2.5 — bounded dropped-item collection

## Scope and permissions

Adds read-only `scan_items`, bounded dropped-item observations in strategic context,
and independently opt-in `collect_items`. The goal binds an entity ID, UUID and
expected canonical item name from observation; the model cannot change permissions.
The scan examines at most 256 entity candidates and returns up to 16 visible stacks
within four horizontal blocks at the same floor level. It reports eligibility,
not a guarantee of pickup. Item NBT and custom display names are not exposed.

`MC_COLLECTION_ENABLED` defaults false. An explicit `MC_COLLECTION_AREA` and
`MC_COLLECTION_DIMENSION` authorize attempts independently of mining and workspace
permissions. Bounds are inclusive block coordinates; feet and drop positions must
be in authorized cells, with the player's horizontal footprint contained inside.
Ownership and pickup delay are not observable. Only approve areas where collecting
these drops is permitted. Minecraft automatic pickup remains active regardless of
this tool's permission and can collect incidental items during any movement,
a failed/cancelled attempt, or while standing still. There is no rollback claim.

## Deterministic execution

Minecraft Java 1.21.1 only. Requires a grounded healthy/fed body in NORMAL risk,
known safe flat terrain, no open container/cursor/grid content, and at least one
empty normal inventory slot. A same-name stack is not assumed mergeable because
item components can differ. Collection does not jump, dig, equip, toss or use
unbounded pathfinding. At most five steps of up to 0.8 blocks use the existing
bounded ground mover, with 50 ms checks, re-observation and target/body identity
checks. The target and body remain within four blocks of the original anchor.
Movement has a six-second budget, near-target pickup waiting 1.2 seconds, inventory
syncs 1.5 seconds each and the arbiter a ten-second overall timeout. Each step
has its own 700 ms bound. Safety/reflex preemption releases controls; late awaited
operations cannot command movement after ownership has changed.

A raw server `collect` packet must name the original target and current body.
Another collector, disappearance alone, or inventory changes alone cannot establish
success. Before/after server `window_items` snapshots must show a positive gain of
the target item type. Pickup during baseline sync is conservatively refused.
Results distinguish reported pickup count, observed inventory gain, partial pickup
and whether those counts match. **Exclusive causality is never claimed:** a
same-type incidental gain may be included. Listeners are cleaned up on success,
failure and cancellation. Mineflayer's internal abandoned inventory-sync wait may
remain until its eventual packet arrives; no follow-on tool movement is allowed.

`COLLECTION-RESULT` diagnostics carry the outcome. Memory writer schema 5 reads
schemas 1–5 and stores collection outcomes as historical records, not commands.
The conservative fallback catalog does not enable collection mutation.

## Automated verification

The collection suite uses deterministic movement/clock fixtures with the real
bounded mover. It covers packet plus snapshot confirmation, missing metadata,
foreign/incidental/partial pickups, ID reuse, UUID mismatch, full inventory,
occlusion, changed terrain, cliffs, danger, area boundaries, moving targets,
time/step budgets, preemption during aim, baseline cancellation and listener
cleanup. Protocol contract checks use the pinned real Prismarine entity/item
metadata decoder and Minecraft 1.21.1 collect packet serializer. Schema-v4 migration
and collection-history restart are covered. These are not live-server tests.
