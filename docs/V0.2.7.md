# V0.2.7 — persistent resource-location memory

## What changed

Local spawn and strategy observations now capture at most 16 visible, allowlisted
resource cells from the existing bounded scanner. Persisted data contains only a
canonical block name, integer block coordinates, world/dimension, local source,
record ID and observation time. Names, Y bounds, coordinate shape, sampled-visibility
marker and four-block eye-to-center range are checked. The marker/range check is
not an independent world raycast or proof of server acknowledgement.

The source is the local scanner, not a cloud goal. The model cannot write resource
records. Goal results and death snapshots do not insert sightings; mining success
or failure is not translated into a supply count or a depletion claim. Custom text,
NBT, ownership guesses and claimed drop yields are not persisted.

## Memory semantics

- One latest sighting per world, dimension and resource cell. A newer sighting at
  that cell replaces its prior block type. Repeated sightings do not create more
  deposits; older clock-shifted observations cannot replace newer records.
- At most 128 resource records inside the existing 500-record total budget. Newer
  events can evict old sightings sooner than the seven-day recall-age limit.
- Seven-day-old and future-dated sightings are not recalled. Expiration is a recall
  filter, not a guarantee of deletion from every saved backup.
- Scope is per agent, configured world ID and dimension. Use a different
  MC_WORLD_ID after a reset; automatic world-reset detection is not implemented.
- Recall is nearest-first, with recency/coordinates as deterministic tie-breakers;
  without an origin it uses recency. The API permits at most 16 results; planner
  context uses eight, independently of the eight historical event memories.
- A recalled entry is either historical_recheck_required or
  matches_current_observation, depending on an exact current local sighting.
  **executionRecheckRequired stays true in both cases.** Current observation is
  not a server-confirmed guarantee of remaining availability at execution time.
- Missing resources remain historical: bounded scans, unloaded chunks, occlusion
  or unknown terrain do not justify declaring them depleted. A changed resource
  type is updated only when that replacement is locally observed.

Resource memory grants no ownership or permission, does not extend mining reach,
load distant chunks, select a route or resume old commands. All actual tools keep
existing region, visibility, equipment, safety and cancellation checks. There is
no shared inter-agent map, learned extraction plan or complete terrain model.

## Persistence and integration

Writer schema 6 reads legacy schemas 1–5 and upgrades on the next write. Sightings
and their source event are written in one serialized snapshot using the existing
lock, backup and atomic rename machinery. Reads validate resource names/coordinates,
per-cell uniqueness and the resource cap. Unsupported schemas fail closed; corrupt
primary snapshots recover only from validated backups. A legacy schema containing
new-format resource records is treated as corrupt rather than silently misread.

The controller recalls resource memories after recording its observation and adds
a separate resourceMemories field to provider context. Read errors are sanitized
and planning can continue with an empty resource-memory context. No additional
provider calls, mutation tools, API cost requirements or configuration flags are
introduced. Local memories stay under ignored runtime/; when cloud planning is
explicitly enabled, recalled resource locations are included in its request.

## Automated checks and limits

The added tests cover persistence/restart, repeated-cell upserts, replacement types,
unknown/absent resources, source boundaries, world/dimension isolation, malformed
and hidden sightings, observation/recall bounds, caller mutation, arbitrary text
exclusion, age/clock behavior, concurrent writes, v5 migration, corrupted/duplicate
records, backup recovery, I/O failure recovery and provider integration without
permission changes. Earlier v1–v4 migration tests now target schema 6.

No live server or real provider calls are claimed. Live testing remains deferred
until the implementation is sufficiently mature, as requested. Current automated
success does not establish Minecraft survival or civilization-level readiness.
